# Idempotency and CORS Best Practices

**Context:** Metaskills Project Research
**Topic:** Idempotency Keys (`x-idempotency-key`) and Cross-Origin Resource Sharing (CORS)

## 1. The Role of `x-idempotency-key`

An idempotency key is a unique value generated by the client and sent to the server alongside a request. It guarantees that the server processes the request exactly once, even if the client retries the request multiple times due to network failures, timeouts, or accidental double-clicks.

### Why it is typically used:
- **Fault Tolerance:** If a client doesn't receive a response (e.g., connection drops), it can safely retry the exact same request. The server recognizes the key, skips processing the logic again, and returns the cached result of the original successful request.
- **Preventing Duplication:** It prevents duplicate database records, duplicate emails sent, or duplicate transactions.

### What types of requests benefit most:
- **`POST` Requests:** In REST APIs, `GET`, `PUT`, and `DELETE` are typically idempotent by design. `POST` requests, however, usually create new resources and are *not* naturally idempotent. Therefore, `POST` requests benefit the most.
- **Payment Processing:** The classic use case (popularized by Stripe). Retrying a failed connection should never result in charging a credit card twice.
- **Order/Resource Creation:** Creating an account, purchasing an item, etc.
- **Quiz Submissions:** While less financially critical than payments, quiz submissions heavily benefit. A user might spend 10 minutes on a quiz. If their internet drops right as they hit "Submit", their client might retry. Without idempotency, this could result in two duplicate submissions, potentially throwing off analytics, grading logic, or failing due to a "user has already submitted" database constraint.

## 2. CORS Preflight Requirements

Browsers use Cross-Origin Resource Sharing (CORS) mechanisms to determine if a web application running at one origin is allowed to access resources from a different origin. 

### The `OPTIONS` Preflight:
When a frontend application makes a "simple" request (like a standard `GET` or `POST` with standard headers like `application/x-www-form-urlencoded`), the browser sends the request directly. 

However, introducing **any custom header**—such as `x-idempotency-key` or `Idempotency-Key`—makes the request "complex." Before sending the actual `POST` request, the browser automatically sends an HTTP `OPTIONS` request (the "preflight") to check if the server permits the custom header.

### Server Requirements to Pass Preflight:
If a client sends an `x-idempotency-key` header, the server's `OPTIONS` response **must** include:
1. `Access-Control-Allow-Origin`: Must match the client's origin (or be `*`, though specific origins are better for security).
2. `Access-Control-Allow-Methods`: Must include the intended HTTP method (e.g., `POST`).
3. `Access-Control-Allow-Headers`: **Must explicitly list the custom header.** (e.g., `Access-Control-Allow-Headers: Content-Type, Authorization, x-idempotency-key`).

If `x-idempotency-key` is missing from the `Access-Control-Allow-Headers` list in the server's response, the browser will entirely block the subsequent `POST` request and throw a CORS error in the frontend console.

## 3. Recommendation for Metaskills Project

### Should we keep idempotency for quiz submissions?
**Yes, absolutely.** Quiz submissions represent significant user effort. A flaky mobile connection during submission should not result in lost data, duplicate database entries, or a generic "Server Error" because a unique constraint was violated on a retry. Using an idempotency key allows the frontend to safely retry a `POST /quiz/submit` request until it gets a definitive response.

### How to configure CORS safely:

To properly support idempotency keys across origins, update the backend API's CORS configuration.

**Recommended Configuration Guidelines:**
1. **Explicitly allow the header:** Ensure `x-idempotency-key` (or `Idempotency-Key`, aligning with the IETF draft standard) is in the allowed headers list.
2. **Cache the preflight:** Use the `Access-Control-Max-Age` header so the browser doesn't send an `OPTIONS` request before *every single* submission. Caching it for 10-24 hours reduces latency.
3. **Restrict Origins:** Avoid `*` for origins if possible; specify the exact frontend domain(s).

**Example Node.js/Express Implementation:**
```javascript
const corsOptions = {
  origin: process.env.FRONTEND_URL || 'http://localhost:3000',
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'OPTIONS'],
  // EXPLICITLY ALLOW the idempotency key header
  allowedHeaders: ['Content-Type', 'Authorization', 'x-idempotency-key'],
  // Cache preflight request results for 24 hours (86400 seconds)
  maxAge: 86400 
};

app.use(cors(corsOptions));
```

Implementing this ensures that the safety of idempotent quiz submissions is maintained without running into frustrating browser-level CORS blockages.
