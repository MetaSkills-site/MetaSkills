ELO Architecture

The MetaSkills application uses a mathematical ELO rating system (originally designed for chess) to dynamically calculate user proficiency and question/vocabulary/passage difficulty over time based on actual performance. This document details the logical workflow, mathematical constants, and explicit codebase integrations that power this system.

1. Core Mathematical Logic & Scaling

The core logic of the ELO engine operates completely out of the utils/elo.js file.

Expected Score Calculation

Before any rating changes, the system calculates the "Expected Score" (probability of the user getting the answer right) using the standard Elo logistic curve: 

// utils/elo.js:12
export function calculateExpectedScore(ratingA, ratingB) {
  return 1 / (1 + Math.pow(10, (ratingB - ratingA) / 400));
}

If a user with a 1400 rating attempts a vocabulary word rated at 1200, the math indicates the user has a high probability (expectedScore > 0.5) of getting it correct.

Rating Adjustment Formula

Once the absolute outcome (actualScore: 1 for correct, 0 for incorrect) is determined, the new rating is calculated using a constant Volatility Factor (K = 32). 

// utils/elo.js:24
export function calculateNewRating(currentRating, K, actualScore, expectedScore) {
  return currentRating + K * (actualScore - expectedScore);
}

If a high-rated user gets an easy question wrong, the penalty is severe because (0 - 0.76) is a large negative chunk multiplied by 32.

Frontend UI Formatting (Display Difficulty)

Raw Elo ratings (e.g. 1104, 1530) are difficult for standard frontend users to digest. To solve this, the backend translates the raw Elo score into a 0 - 100 percentage using a sigmoid curve centered strictly around 1200 (the default starting rating for all users and items). 

// utils/elo.js:39
export function getDisplayDifficulty(eloRating) {
  const x = (eloRating - 1200) / 400;
  const sigmoid = 1 / (1 + Math.exp(-x));
  return Math.round(sigmoid * 100);
}

2. Controller Integrations & Triggers

The ELO system is integrated primarily inside the grading endpoints. It updates the database models asynchronously in a "fire-and-forget" pattern so it never bottlenecks the API response times for the user if the calculation fails.

Vocabulary Engine integration

When a user evaluates a word in the MCQ Vocabulary Marathon, the system hits the verifyVocabularyResponse controller logic.

3. Database Aggregation & Complex Sorting

Because the sigmoid difficulty algorithm (displayDifficulty) is mathematically intensive, running it via javascript mapping is inefficient for large UI data grids.

When an Admin attempts to view all vocabulary or filter by "Hard", the backend explicitly re-writes the Javascript sigmoid equation natively inside a MongoDB Aggregation Pipeline so the DB engine does the heavy lifting before paginating the data.

  • File: controllers/vocabulary.controller.js 
// Add displayDifficulty (mirroring getDisplayDifficulty via sigmoid)
pipeline.push({
  $addFields: {
    displayDifficulty: {
      $round: [
        { $multiply: [ { $divide: [ 1, { $add: [ 1, { $exp: { $multiply: [ -1, { $divide: [ { $subtract: [ { $ifNull: ["$rating", 1200] }, 1200, ], }, 400, ], }, ], }, }, ], }, ], }, 100, ], },
        0,
      ],
    },
  },
});

This is immediately followed by a difficulty band pipeline which translates the 0 - 100 numeric score into string-labels for the frontend:

  • 0-35: "Easy"
  • 36-60: "Medium"
  • 61-80: "Hard"
  • 81+: "Very Hard"
